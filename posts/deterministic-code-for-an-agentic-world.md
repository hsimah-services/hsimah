Much of reliable application engineering is boring. That is a feature. A good feature. Users should not be surprised by inconsistent behavior, and data integrity should not depend on which day a particular getter was written.

Most application plumbing is largely identical. Aside from the particulars of an entity, its getters, setters, mutations, relationships and queries differ primarily by type, name and storage key. A quick audit of one of my personal projects found that nearly 80% of its shipped first-party backend PHP was consistent, repeatable boilerplate.

Generative coding agents are very good at solving the problem in front of them, but they do not have to deal with the consequences of the code they write. That is squarely on my shoulders. In the past two years of working with coding agents, I have seen them be consistently inconsistent with how they complete a given task - on one day an agent may generate a getter with one signature; on another, it may choose a different one. Is it a big deal? I think so. In time these divergent methods may cause issues - more time to reason about the project when starting future work, more context lost to tracking these unique changes. Over time they compound, requiring more conditional branches, more tests and allowing more edge cases.

Agents work fast, and at a scale which can overwhelm humans trying to review all the PRs for the project. As a project grows, this headache multiplies. Often we end up scanning the bulk of the changes, playing “spot the inconsistency” rather than having a solid comprehension of the changes. Such is the downside of using probabilistic tools for deterministic work.
## YAML In, Boring Code Out
![Elephentity logo](/assets/elephentity.svg)
Along with my own agents, I built my own code generator framework - say hello to [Elephentity](https://github.com/hsimah-services/elephentity). As I adopted agentic coding for my personal projects I found myself dismayed at the lack of code quality I was seeing. I am pedantic about what I write, and I was struggling to get the agents to write like me. So, I made sure the agents could only write code like me.

Elephentity turns a concise YAML entity specification into deterministic, signed application code. I picked YAML due to its balance of flexibility and structure, and because it is both readable to humans and agents. Markdown can become overwhelming to humans and agents, config-in-code requires significantly more framework support than I wanted to invest.

A simple entity spec - [a Clog Item](https://github.com/hsimah/clog/blob/main/server/spec/entities/Item.yml) will generate [a read-only `Item` class](https://github.com/hsimah/clog/blob/main/server/generated/Item/Item.php) and [a writable `ItemMutator`](https://github.com/hsimah/clog/blob/main/server/generated/Item/ItemMutator.php) for performing updates.

Files generated by Elephentity are owned by the Elephentity framework. Every generated file includes a content digest. Generation checks reject changes that do not match the deterministic output, so generated files cannot be casually edited by hand. The bundled skills aid agents to navigate the framework efficiently.

All the code generated by Elephentity is consistent, and any changes to how a particular feature is handled (e.g. string field verification) is controlled by the framework. A single change there applies to all entities in a project immediately.
## Elephentity in the wild
As previously mentioned, I used Elephentity to rebuild my [personal inventory tracker, Clog](https://github.com/hsimah/clog). It is a very simple web application, but a good model to use to develop Elephentity.

As of [Comet Corgi](https://github.com/hsimah/clog/releases/tag/1.0), the numbers:
Overall shipped PHP
- 77 files, 5,724 physical lines
- Generated: 55 files, 4,500 lines
- Custom: 22 files, 1,224 lines

In Clog, Elephentity produces
- 78.6% by lines
- 71.4% by files
- 69.3% by bytes

This does not mean 78% of Clog is incapable of containing bugs. It means 55 independently authored implementation surfaces have been reduced to a small number of generator implementations, tests and specifications. When a convention changes, I update it once and regenerate every affected entity consistently.
## Flexible, but Opinionated
Elephentity is opinionated about the parts that should be consistent and deliberately permissive everywhere else. It was designed around controlling what should be controlled and allowing users free rein to do what they want to do outside of that. There are many hooks for custom code execution - Elephentity generates the necessary interfaces, showing the agent the contract it needs to fulfill. Outside of that, custom business logic is not signed. It is up to project maintainers to decide what rules to apply in this space.

To repeat: the generator owns repeatable plumbing; humans and agents own the actual domain decisions. The escape hatches are structured contracts, not flowing bespoke code without rhyme or reason.
## Reuse to reduce
Agents are always reinventing the wheel. Do you need to log something? They will write you a bespoke logging framework. But logging is a largely solved problem, in most projects we should reach for an off-the-shelf solution.

Elephentity supports reuse through pattern specs. A pattern defines a shared capability that can be applied to many entities. A blogging platform, for example, might have `VideoPost`, `ImagePost` and `TextPost` entities. Each needs an owner, creation time and comments, so that shared model and behavior can live in a single `IsPost` pattern. Configure it once, then apply it wherever it belongs.
## Bring your own builder
Elephentity mostly cares about mapping the spec to output - the framework was designed to be opinionated about input and output, not the language used. It currently ships with a PHP code generator and the architecture permits support for other languages, e.g. C#. Generators can be in any language, so long as they meet the IR specification. It is completely feasible to have a single spec generate backend code in two languages!
## Integrations are the spice of life
Another layer of flexibility built into Elephentity is the concept of Integrations. These are third-party add-ons which can hook into the code generation lifecycle. For example, generating GraphQL resolvers and types from Elephentity specs.

By opting into an integration, a project adds its deterministic outputs to the build. GraphQL works this way today; future integrations could provide logging, REST APIs or other shared capabilities.
## y tho?
Good question - I am certainly not expecting anyone to adopt Elephentity for their own projects. It’s for me to meet my needs. It is opinionated and matches my opinions (which are always correct!).

I believe this is the right step to have taken. A blend of determinism and probabilism where we can rely on what we know should be reliable, and allow the agents to focus their efforts where it matters - the bespoke logic every entity has for its specific use case.

The determinism of the code generator prevents the agents independently reinventing every entity over and over. A compact YAML spec is cheaper for agents to read and easier for humans to review.

The division of labor is geared towards each actor’s strengths. Agents are used to improve the machine which writes repetitive code, not to repeatedly improvise the code itself.
## This sounds perfect!
It’s not. It does not design the domain models for you. It does not eliminate custom business logic. The signatures are an integrity check, not a security boundary. A sufficiently determined agent can re-sign a modified file, which is why generation checks and code review do still matter. It does not make everything identical.

The centralization of Elephentity also increases the blast radius of any bugs. A bug in a generator can be reproduced consistently across every entity. The trade-off is that the bug has one implementation to find, one place to fix, and a deterministic set of outputs to verify.

What Elephentity does do is it standardizes the parts that should be identical and exposes contracts for everything else.
## Conclusion
Most business application code should not be surprising. Elephentity makes the repetitive parts deterministic so engineers and agents can spend their creativity on the parts that actually differ.

**Elephants never forget. Elephentity never forgets how the last entity was written.**
